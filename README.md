# Merchant Support Resolver

An autonomous AI teammate for Paytm merchant support (Hackathon Track 3). It does not just answer: it
reads merchant data, decides inside policy guardrails, takes action through tools, and reports back in
the merchant's language (English, Hindi, Tamil).

**The default mode is free.** Python standard library only, a local SQLite file, no API keys, no cloud
services, no paid packages. The demo data is synthetic. Groq is an optional upgrade (see below).

## Run it (2 minutes)

```bash
python app.py            # needs Python 3.9+, nothing to install
# open http://127.0.0.1:8000
python test_agent.py     # 115 tests (Groq is mocked, no key needed)
python app.py --reset    # restore the demo data
```

**On Windows** `python` is often not on `PATH`. Use the project virtualenv instead:

```powershell
.\.venv\Scripts\python.exe app.py
.\.venv\Scripts\python.exe test_agent.py
.\.venv\Scripts\python.exe app.py --reset
```

No virtualenv yet? `python -m venv .venv` creates one. The app itself needs nothing installed — standard library only.

## What the agent does

Understand (language + category) -> Diagnose (tool calls) -> Act (policy-checked) -> Report (merchant's language).

| Merchant | Scenario | What the agent does |
| --- | --- | --- |
| M001 | Settlement failed, bank timeout | Re-triggers the settlement |
| M002 | Settlement pending at bank | Raises a bank ticket, tells the merchant the expected credit date |
| M003 | Soundbox offline (network) | Sends a remote restart |
| M004 | Soundbox hardware fault | Orders a replacement |
| M005 | Chargeback Rs 4,500 with evidence | Submits the transaction proof before the deadline |
| M006 | Chargeback Rs 25,000 | Above the Rs 10,000 auto limit, escalates to a human with a case file |
| M007 | Settlement failed, account mismatch | Not auto-fixable, escalates (never blindly retries) |
| M008 | Healthy | Takes no action and says so |

Any merchant can also ask for a **refund** at any time. Refunds are never auto-approved: the agent collects the
recent transactions, escalates to a human, and says so in the merchant's language.

Guardrails live in the `POLICY` dict at the top of `app.py`. Every tool call and decision is written to the
`audit_log` table and shown in the right-hand panel. `policy_gate()` is the single checkpoint every call passes
through, whichever engine proposed it — actions *and* reads.

### Limits, and what happens when one is reached

Every action the agent can take has a ceiling: **2** settlement retriggers, **2** bank tickets, **2** device
restarts, and chargebacks above **Rs 10,000** go to a human. The counters live on the record, so the cap holds
across turns — a merchant who asks a third time does not get a third ticket.

Hitting a limit is not a failure and not a crash: the gate refuses the action, the case is handed to a human with
the count in the case file, and the merchant is told in their own language why. It also means the agent cannot loop
on a merchant's behalf.

### How a message is routed

The rule-based engine picks a category by **weighted keyword scoring**, not by first match. A distinctive word
("settlement", "refund", "chargeback") outweighs a generic one ("money", "qr"), so "my settlement is not working"
reaches the settlement flow instead of the device flow, and a refund request is never mistaken for a settlement
that could be auto-retriggered.

### Conversation memory

The agent remembers what it just did with that merchant, so a follow-up keeps its context.

- **Follow-ups inherit the category.** "yes please do that" carries no topic of its own, so the agent continues the
  previous turn's category instead of asking the merchant to explain again. Inheritance only happens when the message
  has no keyword of its own *and* either contains a continuation cue ("yes", "also", "any update", "still") or is
  three words or fewer — so a new question like "what is the weather today" correctly starts a fresh conversation.
- **The last four turns go to Groq.** The model is given the recent exchanges and instructed to use them, so it answers
  "did that work?" about the thing the agent just did rather than about the merchant in general.
- **One case per issue.** A follow-up about an issue that is already with the human team does not raise a second case.
  The agent recognises the same record (`settlement:S1007`, `dispute:CB02`, `device:D04`, `merchant:M001`), says the
  case is already in progress and reuses the original case id.

Every turn is already logged to the `tickets` table, so the conversation log needs no extra table.

### Localisation

Replies are written in the merchant's language, including the date ("कल (11 नव)" / "நாளை (11 நவ)" / "tomorrow
(11 Nov)") and the amount, which uses Indian digit grouping (Rs 1,84,500). The escalation reason is localised
too. The detailed English reason and the case file stay in the audit trail for the human agent.

## 3-minute demo script

1. Pick **M001**, click "My settlement has not arrived": watch the retrigger and the audit trail.
2. Type **"yes please do that"** as M001: the agent continues the same settlement conversation instead of asking
   the merchant to explain again. This is the conversation-memory moment.
3. Pick **M002**, click the Hindi chip: reply comes back in Hindi with a bank ticket.
4. Pick **M003**, click "Soundbox is not working", then **M004** for the replacement.
5. Pick **M006** with the chargeback chip: the agent refuses to auto-handle and escalates. Say this is the safety story.
6. Show the **Human handoff queue**: the escalated case with its case file, the reason and what the merchant was told.
   Send **"any update on this?"** as M006 — the case is already with the team, so no second case is raised.
7. Pick **M002** and ask about the pending settlement twice more: the third ask hits the bank-ticket limit, so the
   agent stops and hands the case to a human instead of raising another ticket.
8. Show the Outcomes panel: auto-resolution rate, escalations, average agent time, and the rules-vs-Groq split.

### The human handoff queue

Every case the agent cannot fix inside policy lands in the **Human handoff queue** panel with the facts a human
needs to pick it up: the case id, the merchant, the merchant's own words, why it was escalated, the full case
file the agent prepared (the settlement, dispute, device or transaction rows it read), and the reply the
merchant was given, in their language. Each card is tagged with the engine that handled it. The queue refreshes
with every message and clears on "Reset demo data".

### How the outcomes are measured

The **auto-resolution rate** is the share of cases the agent decided on its own that it also resolved:
`resolved / (resolved + escalated)`. A message the agent could not classify is a clarification request, not a
resolution failure, so it is excluded from the denominator and the panel says how many were excluded. Escalations stay
in it — handing a case to a human is not an auto-resolution.

**Avg agent time** is the average over *all* tickets, so it mixes a rule-engine run (milliseconds) with a Groq run
(network latency) and the two are not comparable on that number. The apples-to-apples comparison is the per-engine
tiles — *Avg time · rules* and *Avg time · Groq* — which are shown separately.

### Rules vs Groq

Every conversation records the engine that answered it and, for Groq, the model that was used. The Outcomes
panel shows the split — how many conversations each engine handled and how long each one took on average — plus
the model name in use. A Groq request that fails is counted as a **fallback** and the rule-based agent answers
instead, so a degraded run is never silently counted as a Groq success.

## Reliability under a rate-limited API

The Groq key on this project is shared, and its measured limits are 1,000 requests/minute and 8,000 tokens/minute
(see the rate-limit note below). Four things keep a throttled or flaky API from turning into a broken demo.

**1. Retry with backoff.** `groq_chat()` retries a request that comes back HTTP 429 or 5xx, up to `GROQ_ATTEMPTS = 3`
times, with a growing pause between attempts (`GROQ_BACKOFF = (2, 6)` seconds, capped at `GROQ_MAX_WAIT = 12`). The
wait honours a `Retry-After` header first, then the "try again in 5.8725s" hint Groq puts in the error body, and
only then falls back to the fixed backoff. A request that is worth retrying gets a second chance instead of
dropping straight to the rule engine.

**2. Only the tools that fit the category are offered.** The agent has 9 tools, but a settlement question does not
need the device-replacement tool. `tools_for_category()` builds the tool list per request: all the read tools (they are
gated and harmless) plus only the action tools that make sense for the classified category, plus `escalate_to_human`.
That cut the prompt from **672 to 517 tokens — 21% fewer** — which matters directly against a tokens-per-minute
limit, and it stops the model reaching for an irrelevant action.

**3. The restriction is enforced in code, not in the prompt.** `run_tool(allowed=...)` refuses any tool that was not
offered for that request, even if the model asks for it anyway. The refusal is written to the audit trail as
`… was not offered for this request`. It does not trigger the deny-then-escalate net — the model may still read and
answer — but the action cannot happen.

**4. A case is never left unhandled.** If the model only *describes* a case instead of acting on it, the rule
engine's verdict decides (`Agent.rule_flow()`), reusing the same one implementation of policy. A dispute over the
limit still reaches a human even if the model rambles. When the rule engine acted or escalated, the merchant's reply
is rebuilt from the template, so the message always matches what actually happened.

## Using the Groq API (optional)

Without a key the agent is rule-based and fully free. With a key, **Groq runs the agent**: it reads the
merchant's message, chooses which tools to call, and writes the reply in the merchant's language.

```bash
cp .env.example .env      # Windows: copy .env.example .env
# then put your key in .env (GROQ_API_KEY=...)
python app.py --check-groq   # proves the key, model and tool calling work, then exits
python app.py             # header shows "Use Groq"; untick it to compare with the rule-based agent
```

The default model is `openai/gpt-oss-120b` (it supports tool use). Groq retired `llama-3.3-70b-versatile` for
free and developer tiers on 16 Aug 2026, so an older `.env` will fail with HTTP 404 until `GROQ_MODEL` is
updated. Model names change, so check https://console.groq.com for the current list and set `GROQ_MODEL` if needed.
Note that a real `GROQ_MODEL` environment variable overrides the one in `.env`.
Check your Groq rate limits before the finals.

**Rate limits, measured on this key:** 1,000 requests/minute and **8,000 tokens/minute**, shared across models. One
turn costs 2-4 requests (a tool call, its result, the answer) of roughly 1,200 tokens each, so a handful of quick
clicks exhausts the minute and Groq answers HTTP 429. When that happens the rule-based agent takes over and the audit
trail says why, so nothing breaks — but pace the demo with a pause between chips, or switch to
`openai/gpt-oss-20b`, which spends fewer tokens per request.

How it stays safe (this is your pitch point):
- Groq never executes anything itself. Every action goes through `policy_gate()` in code, including the rule-based path.
- `merchant_id` is injected by code for read tools, and the gate rejects record ids that belong to another merchant.
- **Every tool call passes the gate, reads included.** A read that names another merchant is refused and written to the
  audit trail, so no code path — rule engine, Groq, or anything added later — can hand one merchant another's data.
- A denied action returns to Groq as an error. If Groq still does not escalate, code escalates for it and replies from a fixed template, so a model cannot claim a fix that did not happen.
- If the API fails, the rule-based agent takes over and the trace says why.
- The key lives in `.env` or an environment variable and is never sent to the browser.

## Tests and CI

```bash
python test_agent.py          # 115 tests, no API key needed (Groq is mocked)
```

The suite covers the classifier routing, the localised replies, the model id, the handoff queue, the engine
tracking, the conversation memory, the auto-resolution rate, the read-path gate, the action caps, the retry and
backoff behaviour, the per-category tool trimming, the safety net, and the HTTP API itself — the last one boots a
real `ThreadingHTTPServer` on a random port and exercises every endpoint plus the error paths (empty message,
malformed JSON, a non-UTF-8 body, 404 and reset).

`.github/workflows/tests.yml` runs the suite on Python 3.9, 3.12 and 3.13, then starts the server and smoke-tests it,
so a change that only breaks on a newer interpreter is caught before the finals.

## Going to production

Each `tool_*` method in `app.py` is a stub over SQLite. Replace its body with a call to Paytm's real
settlement, device, dispute and ticketing APIs; the agent loop, policy checks and audit log stay the same.
